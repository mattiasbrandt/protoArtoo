# =============================================================================
# tools/bench_rows/firebeetle2.txt
#
# The replayable sheet for the FireBeetle 2 (ESP32-P4) Console bench runbook
# (#215), commands only -- everything #215 lists that the Console Client's
# scripted mode (#264) can express. Human-only steps (physical attach/detach,
# flashing, pressing heap from a browser) are `pause` directives; what a row
# is expected to answer stays on #215's own criterion, never written here
# (docs/console-protocol.md's "no expect directive" decision) -- a reviewer
# reads the transcript against the linked ticket.
#
# Run with either adapter:
#   python3 tools/console_client.py --port /dev/ttyACM0 --script tools/bench_rows/firebeetle2.txt
#   python3 tools/console_client.py --http http://<host> --script tools/bench_rows/firebeetle2.txt
#
# Select rows (by name only, e.g. "detach-replug" -- not the ticket number):
#   --rows detach-replug,tab-completion   (explicit order, not file order)
#   --skip-manual                         (every row with no `pause` -- agent-runnable)
#
# After this ticket, #215 owns edits to this file (ticket body, "Rows").
# =============================================================================

# #260 / #275 - detach / reconnect. A partial command left mid-line survives
# a detach as an empty, correctly-reprinted prompt, not as an inherited
# fragment, and the serial side comes back on its own after the replug
# (#275's settle window). The board MUST be powered from its OTG port for
# this row: pulling the CDC cable on a USB-powered P4 is a reboot, not a
# detach. The client reconnects by itself once the port is back, so every
# step the operator takes happens BEFORE pressing Enter at the pause.
#
# Cut on purpose (2026-09-05, #274): the "detach with `help` still printing"
# variant that stood here. A listing finishes within about a second of the
# detach on a host that keeps reading, and a hand replug lands seconds later,
# so a replug cannot reach the firmware mid-emission from this bench; nothing
# a person can do here evidences that cell, and the paused client cannot type
# the listing for them.
@row 260 detach-replug
raw drive.action.mo
pause Step 1: unplug the CDC cable from the board (the board stays powered from the OTG port).\nStep 2: wait 5 seconds.\nStep 3: plug the CDC cable back in.\nStep 4: wait 5 seconds.\nStep 5: press Enter here, in this pane. The client reconnects by itself and sends the next command.
send system.status.health

# #243 - the WiFi module reboot that makes #189's bounded recovery ladder
# provable on the shipping image instead of only in bringup/p4_hosted_bench.cpp.
# Serial only, deliberately: over WiFi the answer would travel on the link the
# command takes down. What the row must show is on #243.
#
# The ladder notices the module has gone when an SDIO WRITE fails, so an idle
# controller may not detect it promptly - keep a dashboard tab or an SSE client
# connected while this row runs, or you are timing the next write rather than
# the recovery (#243 worker finding, 2026-09-06).
#
# A healthy fitted module recovers on attempt 1, so this row proves the ladder
# STARTS AND RECOVERS. It is not expected to reach terminal Degraded, which
# needs five consecutive failures; do not read its absence as a failure.
@row 243 wifi-module-reboot
send system.status.health
send system.action.reboot-wifi-module
listen 40
send system.status.health
pause Watch the link drop and come back. The board must stay up throughout: uptimeMs keeps climbing and resetReason does not change - it is the module that restarted, not the controller. Press Enter when the link is back.
send system.status.health

# Epic #175 Wave 0 -- the capability lines on the second Board Variant
#
# Added 2026-09-11, operator direction, as the P4 half of the block in
# tools/bench_rows/artoo_esp32.txt:137+. Same rule as that block and as this
# sheet: what a row must answer stays on the Closing Ticket (#355), never here.
#
# This sheet covers both P4 boards, and they are NOT equivalent for Wave 0.
# Board 1's C6 is permanently unflashable, so board 1 has no WiFi and no HTTP:
# on it, a Wave 0 capability whose ACTION arrives on POST /api/config is
# unavailable rather than merely awkward, and the three rows below marked
# "needs a working C6" cannot be run there at all. A P4 whose C6 works reaches
# the LAN normally (PA_CAP_HOSTED_WIFI is 1 on this chip arm) and carries the
# full set, exactly as artoo does.
#
# So the cuts below are BOARD 1 cuts, not P4 cuts. Read them as:
#
#   - A7's sound member (#340): a Component Member is SET on POST /api/config
#     and no console operation writes one (src/console/console_catalog.cpp has
#     sound.action.* and sound.config.volume, nothing that selects a member).
#     The READ half is folded into the vocabulary row below. On board 1 the
#     change half cannot be performed at all; on a working-C6 P4 it runs as
#     the-sound-member-survives-a-reboot-on-the-p4 below.
#   - A2/A3/A4's calibration crossing (#338 #342 #345): the distinctive
#     pre-migration endpoints are written on POST /api/config too -- the catalog
#     carries servo.action.* but no servo.config.* -- so the one-shot cannot be
#     aimed on this board. What IS reachable from the console is the migration
#     PATH; that is the second row below, and it claims less.
#   - A6's Board Lanes (#339): board_lanes is emitted only by GET /api/identity
#     (src/web/api_identity_serializers.cpp). The console's
#     system.api.get-identity deliberately answers with the two ConfigSnapshot
#     fields and NOT the board manifest (consoleExecuteSystemApiGetIdentity,
#     src/console/console_module.cpp), so there is nothing here to read.
#
# Ceiling for this block, as for artoo's: Controller Upload Verified. The bench
# is unseated; a row wanting a moving arm is Not Assessed and says so.
# =============================================================================

# A1a-A1d (#337 #356 #357 #358) - "Every part on your droid has a name the
# firmware and the browser both know", and since #358 a Part is nameable whether
# or not this body drives it. This is the one Wave 0 row a SECOND board can
# falsify: the P4's Board Capability Gates are not artoo's, so if the catalog
# were ever the drivable subset rather than the whole vocabulary, this is where
# the list comes back short. get-components names every Part with its own gate
# and included flag, so the gate VALUES are what may differ between the two
# boards and the Part LIST is what must not. sound.status.current is the A7 read
# half: which member this board reports fitted, on a board whose audio lane is
# shared with protor2link.
@row 358 the-part-vocabulary-on-the-second-board
send system.api.get-components
send sound.status.current

# A2/A3/A4 (#338 #342 #345) with A8 (#375) and A9 (#376) - the migration PATH on
# a second board's real NVS. system.action.set-mode calls saveConfigToNvs()
# (include/console_direct_action_system.h), which runs configSaveServoOutputs()
# before configSave() (src/main.cpp) -- so an ordinary mode change IS a full
# config save and performs the migration, which is why "don't touch servo
# settings" is not sufficient guidance to a bench operator. Native tests reach
# this sequence against a stubbed Preferences; what they cannot reach is flash,
# and this board's NVS partition is not artoo's. Since A8 a write that did not
# reach flash reports err rather than ok, so the record this row returns is
# itself the evidence. It does NOT prove a builder's calibration crossed: that
# needs distinctive pre-migration values this board cannot be given.
# Nothing here reads the endpoints back: servo.status.current is is_query:false
# in the catalog -- a field descriptor, never an executable command (it answers
# not-executable, measured on artoo 2026-09-11) -- and there is no
# servo.config.* operation and no HTTP on this board. So this row evidences the
# save and the board's survival of it, and #355 says plainly that the values
# themselves are unreadable here.
@row 345 the-first-save-migrates-on-this-board
send system.status.health
send system.action.set-mode mode=stationary
send system.status.health
send system.action.reboot
pause Wait for the board to come back, re-attach, then press Enter
send system.status.health
